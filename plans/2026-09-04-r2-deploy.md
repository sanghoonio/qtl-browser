# R2 data deploy

Cloudflare account "topchef", bucket `qtl-browser`.

- S3 endpoint: `https://02604ac525a365f5ff995694d8c3da5a.r2.cloudflarestorage.com`
- Public dev URL: `https://pub-50e5b2fc28324ce29d894eba50691039.r2.dev`

## Steps

1. `pipeline/config.yaml` gains an `r2:` block (bucket, endpoint, public URL, allowed origins).
2. `pipeline/upload.py`: `cors` applies the bucket CORS rule, `sync` uploads the upload set
   with `aws s3 sync` against the R2 endpoint, `check` fetches a footer range from the public
   URL and confirms 206 plus the CORS headers. Credentials come only from the environment
   (`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`), never from a file in the repo.
3. `ui/.env.production` sets `VITE_DATA_BASE` to the public URL, so `npm run build` targets
   R2 and `npm run preview` is the end-to-end rehearsal. `VITE_DATA_BASE=` (empty) builds a
   local-data bundle.
4. Sam creates an R2 API token (Object Read & Write, this bucket only), exports the two
   variables, runs `cors`, `sync`, `check`.
5. Pages project from the GitHub repo, build command `npm run build` in `ui/`, output `dist/`.
   Then add the Pages origin to `allowed_origins` and re-run `cors`.
6. Later: custom domain on the bucket instead of r2.dev, and the Pages origin behind it.

## What this changes elsewhere

- **Every range request is a Class B operation** against 10M/month free. A gene page is 20 to
  40 requests; the landing page about 5. Nothing to do unless traffic becomes large.
- **Re-running the pipeline changes files in place**; the next `sync` re-uploads only the
  files whose size or mtime changed. Removed tables need `--delete`.
- **The manifest is the contract**: `manifest.json` is uploaded too, so the About page counts
  and table list follow the bucket, not the local build.
- **`npm run build` now targets R2 by default.** Local-data production builds need
  `VITE_DATA_BASE=` on the command line.
- **Wasm compression on Pages** is still unconfirmed; the first-visit 36 MB wasm is the
  largest transfer and is served by Pages, not R2.

### 2026-09-04, range reads were not happening

- The read-only audit (`2026-09-04-r2-parquet-audit.md`) found that DuckDB-WASM defaults to
  `forceFullHTTPReads` and `db.ts` never overrode it, so every parquet read fetched the whole
  file: a cold FLNC page pulled the 155 MB chr7 eQTL file. Every per-page byte figure in this
  log before today was computed from parquet metadata and assumed ranged reads.
- Fix: `db.open({ filesystem: { forceFullHTTPReads: false, allowFullHTTPReads: true,
  reliableHeadRequests: true } })` after `instantiate` in `db.ts`.
- Verified with the shipped wasm run under Node with a curl-backed XHR against the bucket:
  before, the FLNC row-group query was one `GET 200` of 155,414,796 bytes in 77 s; after, 9
  requests (HEAD probes, `bytes=0-0`, the footer, then row-group ranges) all `206`, about
  1 MB, 3 s; a second query on the same file was 3 requests with the footer cached.
- Also seen: the first `read_parquet` autoloads the parquet extension (3.2 MB) from
  `extensions.duckdb.org`, a third host after workers.dev and jsDelivr.
- Audit options B and H applied (Sam declined C, a custom domain). B: every table file is
  registered by relative path at boot with `registerFileURL` and queried by name, which
  removes the HEAD DuckDB sends per query to resolve a raw URL (harness: 4 queries 29 → 25
  requests, the plain `HEAD 200`s gone). H: the eQTL and sQTL credible-set tables are read
  from the materialized locus window (`onCredibleSets` on `LocusPlot`) instead of a separate
  range read of `credible_sets.parquet`; that file is now only read by the variant page.

### 2026-09-04, Worker route for /data

- With the layout fixed, Sam's browser still showed small range requests (0.5–17 KB, HTTP
  206) taking 2–17 s on r2.dev, most often the first touch of a file, while the same ranges
  from curl on his machine were 105–190 ms and from here 110–170 ms. Fresh connections are
  fine, reused ones stall: r2.dev is HTTP/1.1 and the browser's kept-alive sockets die between
  DuckDB's spaced-out requests, then time out before retrying.
- D10 (Sam): `/data/*` is served by the Worker itself from an R2 binding (`worker.js`,
  `r2_buckets` in `wrangler.jsonc`, `run_worker_first`), over HTTP/2 on the site's origin;
  `VITE_DATA_BASE` is empty so production reads `/data` like dev and preview. Range requests
  are parsed by R2 (`range: request.headers`), responses carry `Content-Range`, `ETag`,
  `Accept-Ranges`, and `Cache-Control: public, max-age=3600` (manifest `no-cache`). No edge
  cache yet. Cost: Workers free tier, 100k requests/day, ~5k gene pages. r2.dev stays on for
  `upload.py check`.

- Through the Worker the stalls shrank to two per page but did not vanish: 4.2 s and 20.06 s,
  both right after responses served from Chrome's disk cache. 20 s is Chrome's HTTP-cache
  lock timeout: all range requests to a file share one cache entry (same URL), a stored 206
  makes later overlapping ranges take the sparse-cache path and queue on the entry lock. The
  keep-alive theory above was wrong; curl and the Node harness never stalled because neither
  has a cache. Fix: `Cache-Control: no-store` on everything the Worker serves from the bucket.

- With no-store deployed the stalls remained, and then reproduced from here through the
  Worker: a gene's files stall on first read (ACTN2 cold: 14 requests over 0.5 s, worst
  20 s) and are clean on the second pass. Cold objects stream at 55–80 KB/s through r2.dev and
  the Worker alike (2 MB range 25–44 s; a 17.6 MB file 280 s), warm ones at ~5 MB/s. Warmth
  is per byte range (reading the first 512 KB does not warm the rest), lasts at least 15 min,
  is not multipart-related (single-part upload equally slow), objects are STANDARD class, the
  bucket is ENAM and this machine hits IAD. Parallel cold reads scale (8 × 1 MB in 21 s).
- Cloudflare status at the time: "Elevated number of R2 503 errors in Eastern North America
  region", identified 2026-09-04T21:10Z, plus a WNAM R2 incident earlier the same day. The
  cold-read behaviour matches a degraded R2 region, not the layout, the browser, or the
  transport. The cache-lock and keep-alive theories above were wrong; both fixes are harmless
  and stay. Re-measure cold reads after the incident clears before changing anything else.

- D11 (Sam): both dropped. The working tree is back to the pre-Worker state of `7314f61`
  for the config, env, upload script, queries, and README (commits `e6d0bc6` and `b73ec12`
